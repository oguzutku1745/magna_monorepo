# M1-M5 reviewer status — 2026-09-03

This file maps the August 2026 review to the current pre-release repository. It does not declare
M5 accepted before `@magna/client` is published; package publication remains owner-operated.

## Original blockers

### Blocker 1 — forged Passport A1 claims: closed by A2

The current A2 wrapper recursively verifies the pinned zkPassport outer proof and constrains the
disclosure, age, Bind, FaceMatch/profile, identifier, and output commitments to the witnesses used
for Magna claims. The API receives and verifies the wrapper proof rather than cross-checking detached
prover-supplied claims. Production and developer profiles are separate hash-pinned artifacts.

### Blocker 2 — Ghost/identifier takeover: closed for the implemented V3 flow

Ghost possession now identifies and spends the rooted recovery capability but cannot select a
destination. A fresh zkPassport proof binds destination, nonce, deployment, root, claims, expiry,
and message-secret hash. The EVM portal verifies it against registry state and sends the exact
authorization through Aztec's canonical Inbox. `recover_root_v3(...)` requires both the Ghost-owned
note and that destination-bound message and consumes each once. The Magna API/orchestrator is absent
from the authority path.

Gate B-dev passed with the official mobile developer proof and actual EVM/Aztec transition.
zkPassport confirmed on 2026-08-25 that OPRF does not work with dev mode and has no ETA. Therefore
the local Docker/M1-M5 lane correctly uses the official `NON_SALTED_MOCK = 2` proof. A real supported-
document `SALTED = 1` run will be performed during testnet deployment as an M6/release gate; it does
not require a fork of the zkPassport mobile application.

## M3 verification and metering: closed

The private verification gate and sponsored metering path are implemented and tested atomically.
The remaining receipt-event choice is now resolved by explicit scope decision:

> Privacy-preserving receipt events are formally descoped from M3. The relying party receives the
> signed verification result and transaction hash; aggregate metering remains atomic.

Typed private receipt events are therefore not unfinished M3 work. In the implemented design, the
quoted “signed verification result” is the passkey-authorized Aztec transaction plus the sponsor's
request-bound nullifier, not a signature from a Magna-held key.

## M4 adapter and recovery language

The two live adapters are Passport A2 and Instagram V2. Instagram is DKIM/email based, not OAuth.
Its real proof, source-audited compiler diagnostics, governed DKIM-key commitment, browser-only PII
handling, API substitutions, and Aztec witness binding are reviewer-runnable.

Root Recovery V3 rotates the rooted passport note set. Instagram V2 uses the rootless lane, so after
opening the recovered wallet the holder runs the normal client-side Instagram issuance flow with a
fresh signed Instagram security email. The browser verifies and proves the email locally; neither
the email nor plaintext handle is sent to Magna API.

## Deliberately separate properties

- Rooted Passport A2 issuance emits a contract-siloed nullifier derived from the proof-bound scoped
  identity. A second initial rooted issuance for the same identity is rejected even if owner, Ghost,
  claims, or expiry are changed. The precise boundary is one scoped zkPassport identity per issuer
  deployment, not one biological human across multiple or replacement documents.
- The Docker/local orchestrator is an official public Aztec initial test account by design.
  Production signer custody and rotation are M6/non-local deployment work.
- The frontend P-256 session assertion key has been removed. Login with Magna now uses the user's
  passkey-authenticated Aztec verification transaction. The active sponsor emits an exact request-
  and policy-bound nullifier only after successful verification; `@magna/client` recomputes it,
  silos it to the pinned sponsor, and requires it in the mined successful transaction effect. No
  Magna backend or shared signing private key is a login authority.
